# 権限モデル設計 (Permission Design)

## 1. グローバルロール
ユーザーは以下のいずれかのロールを持つ。

1. **システム管理者 (SystemAdmin)**: 全てのアプリ、ユーザー、設定にアクセス可能。
2. **アプリ作成者 (AppCreator)**: アプリの作成が可能。自分が作成したアプリの管理権限を持つ。
3. **一般ユーザー (StandardUser)**: アプリの利用（レコード追加・編集など）が可能。アプリは作成できない。
4. **閲覧ユーザー (Viewer)**: レコードの閲覧のみ可能。

## 2. アプリ別権限
アプリの「公開範囲」および「権限」は `app_permissions` テーブルで管理する。
権限フラグ： `can_view`, `can_add`, `can_edit`, `can_delete`, `can_manage`

公開範囲ターゲット：
- **非公開**: 誰にも公開しない
- **全ユーザー**: ログイン可能な全員
- **指定ユーザー**: 特定のユーザーID
- **指定グループ**: 特定のグループID

## 3. 権限判定ロジック (Guard / Middleware)
APIへのアクセス時、以下の優先順位で権限を判定する。

1. **システム管理者** なら全許可。
2. アプリの **所有者 (created_by)** なら管理権限(can_manage)を含め全許可。
3. **ユーザー個別権限** が設定されていれば、それを優先適用。
4. 所属する **グループの権限** が設定されていれば適用（複数グループに所属する場合は権限をORで結合）。
5. **全ユーザー公開** の権限が設定されていれば適用。
6. 上記すべてに該当しなければ **アクセス拒否 (403 Forbidden)**。

## 4. UIの制御
フロントエンドは、APIから返却される「自分の権限」に基づいて、追加ボタンや編集ボタンの表示/非表示を切り替える。ただし、UI上の非表示はUXの向上目的のみとし、最終的なアクセス制御は**必ずバックエンドで行う**。
