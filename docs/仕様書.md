# 1. 最重要前提

* 完成品はローカルデスクトップアプリではなく、サーバ型Webアプリとする
* Windows10上にサーバを構築し、LAN内のユーザーがブラウザからアクセスして利用する
* インターネット接続なしで利用できること
* 外部API、クラウドDB、外部CDN、オンライン認証、SaaS連携は禁止
* すべてのデータはサーバPC内に保存する
* 認証と認可を必須とする
* ユーザーは業務アプリを作成し、公開範囲を指定して公開できる
* UIの既定は日本語とする（v0.1.0時点で日本語・英語の切替に対応済み。業務データは自動翻訳しない）
* kintoneのように、ユーザーがノーコードで業務アプリを作成・共有・利用できること
* フロントエンドの表示制御だけで権限を守ってはいけない
* すべての重要APIでバックエンド側の認可チェックを必須とする

# 2. 推奨技術構成

## Frontend

* React
* TypeScript
* Vite
* React Router
* TanStack Query
* 通常CSSまたはCSS Modules
* 外部CDN禁止
* フォント、アイコン、画像はローカル同梱

## Backend

* Node.js
* TypeScript
* NestJS推奨
* REST API
* Zod または class-validator による入力検証
* 認証ミドルウェア
* 認可ガード
* 監査ログミドルウェア

## Database

* PostgreSQL
* Prisma ORM推奨
* recordsテーブルの業務データはJSONBで保存
* マイグレーション管理必須

## File Storage

* 添付ファイルはサーバ内のローカルフォルダに保存
* DBにはファイルメタデータのみ保存
* 保存ファイル名はUUID化し、元ファイル名とは分離する
* パストラバーサル対策を必須とする

## Runtime / Deploy

* Windows10サーバ上で起動
* LAN内ブラウザからアクセス
* インターネット不要
* `.env` による環境設定
* 起動手順書を作成
* バックアップ手順書を作成

# 3. MVP機能

## 3.1 認証

* ログイン
* ログアウト
* パスワード変更
* 管理者によるユーザー作成
* ユーザー有効化 / 無効化
* 初期管理者ユーザーの作成
* パスワードハッシュ化
* セッションまたはJWTによる認証
* ログイン失敗時のエラーメッセージは過剰に詳細化しない

## 3.2 認可

以下のロールを実装する。

* システム管理者
* アプリ作成者
* 一般ユーザー
* 閲覧ユーザー

ロールだけでなく、アプリ単位の権限を必ず実装する。

## 3.3 グループ管理

* グループ作成
* グループ編集
* グループ削除
* グループへのユーザー追加
* グループからのユーザー削除

## 3.4 アプリ管理

* アプリ一覧
* アプリ作成
* アプリ編集
* アプリ削除
* アプリ複製
* アプリ公開 / 非公開
* 公開範囲設定
* 自分が利用可能なアプリ一覧
* 自分が作成したアプリ一覧

## 3.5 アプリ公開範囲

以下の公開範囲を実装する。

* 非公開
* 全ユーザー公開
* 指定ユーザー公開
* 指定グループ公開

公開先ごとに以下の権限を設定できること。

* 閲覧
* 追加
* 編集
* 削除
* 管理

## 3.6 フォームビルダー

アプリごとにフォーム項目をノーコードで作成できること。

対応フィールド:

* 文字列1行

* 数値

* チェックボックス
* ラジオボタン
* セレクトボックス
* ユーザー選択

* 添付ファイル
* 自動採番

* 左：フィールド部品一覧
* 中央：フォームプレビュー
* 右：選択中フィールドの設定

## 3.7 レコード管理

* レコード一覧
* レコード詳細
* レコード新規作成

## 3.8 ビュー管理

* 絞り込み条件設定

# 4. DB設計方針

ノーコード業務アプリのため、アプリごとに物理テーブルを作成するのではなく、メタデータ方式を採用する。

主なテーブル:

* users
* groups
* group_members
* apps
* app_permissions
* fields
* records
* record_comments
* record_histories
* views
* attachments
* audit_logs
* settings

recordsテーブルでは、各レコードの値をdata_jsonとして保存する。

# 5. 権限判定ルール

以下の順で権限を判定する。

1. システム管理者なら全許可
2. アプリ所有者なら管理許可
3. ユーザー個別権限があれば適用
4. 所属グループ権限があれば適用
5. 全ユーザー公開なら既定権限を適用
6. それ以外はアクセス拒否

すべてのAPIで認可チェックを必ず実装すること。

フロントエンドのボタン非表示だけで権限制御したことにしてはいけない。

# 7. ノーコードApp Hooks / Workflows設計

可能であれば、`.agent/workflows/` に以下のワークフローを作成してください。

## 7.1 pre-implementation-review

目的:

実装前に、設計抜けを防ぐ。

実行タイミング:

* 大きな機能を実装する前
* DBスキーマ変更前
* 認可ロジック変更前

実行内容:

* 要件との整合性確認
* 影響範囲確認
* DB変更有無確認
* API変更有無確認
* 権限影響確認
* テスト計画作成

## 7.2 post-schema-change-check

目的:

DBスキーマ変更後の破綻防止。

実行タイミング:

* Prisma schema変更後
* migration追加後

実行内容:

* migration生成確認
* seedデータ更新確認
* 型生成確認
* 既存API影響確認
* records.data_jsonとの整合性確認

## 7.3 authz-guard-check

目的:

認可漏れを防ぐ。

実行タイミング:

* API変更後

* すべての重要APIに認証ガードがあるか確認

## 7.4 post-frontend-change-check

# 10. 品質条件

* TypeScriptエラーがないこと
* フロントエンドとバックエンドのbuildが通ること
* 主要APIに認証チェックを入れること
* 主要APIに認可チェックを入れること
* パスワードを平文保存しないこと
* 外部CDNを使わないこと
* インターネット接続なしで起動できること
* ダミーデータを用意すること
* 管理者、アプリ作成者、一般ユーザー、閲覧ユーザーで動作確認すること
* アプリ公開範囲ごとのアクセス制御をテストすること
* 削除操作には確認ダイアログを出すこと
* CSVエクスポートは権限チェックを必須にすること
* 添付ファイルはサーバ内の指定フォルダに保存すること
* 添付ファイルの直接URLアクセスで権限を迂回できないこと
* 監査ログが主要操作で記録されること
* セットアップ手順書を作成すること
